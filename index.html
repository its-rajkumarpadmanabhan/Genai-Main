Email notification system

Sends in a background thread so nothing blocks the API response — and always re-queries the database for the current email before sending.

When emails are sent

Doctor accepts appointmentPatient + assigned caretaker
Doctor rejects appointmentPatient + assigned caretaker
Doctor marks On LeavePatient + assigned caretaker
Forgot password requestPatient / Doctor / Caretaker

Reliability

  • ✓ Runs in a background thread — never blocks the API response
  • ✓ Always queries fresh from the database — never a stale or cached email
  • ✓ Supports Gmail SMTP (App Password) or any SMTP relay, e.g. SendGrid

Requirements & bug fix log

Consolidated dev handoff notes — bug fixes, appointment rules, connection workflow, and profile requirements, organised by area.

1. Bug fixes priority
1.1 Appointment booking errors
  • Caretaker booking throws assignedPatients.forEach is not a function — must be corrected.
  • Caretaker must be able to select a date when booking an appointment.
  • Appointment request and confirmation details are not appearing on patient or caretaker profiles after booking.
  • Patient-to-caretaker request fails with "Caretaker not found." — must be corrected.
1.2 Notifications
  • Close button on the caretaker's alert (triggered by a patient notification) does not work — must be corrected.
1.3 Doctor profile
  • On a doctor's profile, "Assigned Patients" shows a leftover/previous preview instead of the default "No profile preview" state when nothing is selected.
  • Doctor cannot mark an appointment as Missed for today or tomorrow — this should only be allowed once the appointment date has passed.
  • Filter option on the profile page does not work — must respect the filter selected by the user.
1.4 Admin dashboard
  • Admin dashboard structure has not been updated. Apply the template/structure from adminsdashboard.html to admin-dashboard.html.
2. Appointment system core
2.1 Booking rules
  • A caretaker can book a doctor appointment using the patient's ID; the request must also appear on both the patient's and caretaker's profiles.
  • If a patient books their own appointment, show "🩺 Booked by Patient: [Patient Name] | [ID]" on the patient profile, visible to doctor and caretaker as well.
  • When a caretaker books on behalf of a patient, the patient's profile should show the booking as "Booked by Caretaker: [Caretaker Name]."
  • Regardless of who books, neither party should see full booking details until the patient and caretaker are connected.
  • Only doctors may initiate/conduct video call appointments — not patients or caretakers.
  • When booking, the appointment type (Online / Offline) must be specified.
2.2 Appointment ordering
  • In the caretaker's "Patient Doctor Appointments" list and the patient's "My Appointments" list, the most recent/last appointment should appear first.
  • General rule: appointments are shown first-booked-first; Completed and Missed appointments move to the bottom of the list.
2.3 Doctor-side behavior
  • If a doctor switches "Today's Availability" to "On Leave Today" after accepting a booking, the affected patient/caretaker receive a popup: "Today's appointment cancelled by doctor because doctor is on leave today," and the patient's status updates to "Cancelled by Doctor."
  • Doctor can upload a prescription in PDF format for online and offline appointments; patient and caretaker view it via a "Prescription" button on the current appointment.
  • Add a search option in "Patient Appointments" (doctor view) to look up patients by name or ID, filtered by status (upcoming, completed, awaiting approval).
2.4 Request status visibility
  • When a patient sends a request to a doctor, show "Waiting for confirmation — [Doctor Name], [Date], [Time]" on the patient profile, visible to any caretaker viewing it.
  • Caretaker-booked requests show the same "Waiting for confirmation" status on the caretaker's profile; the caretaker must supply the patient ID to complete booking.
  • Colour-code appointment statuses: Rejected, Completed, and Missed should each have a distinct colour.
3. Patient–caretaker connection workflow core
  • Patients may send requests to up to 5 caretakers at a time; caretakers may accept up to 2 patients at a time.
  • If a request is rejected or a patient/caretaker is removed, the other party is freed up to connect elsewhere.
  • Each profile should have categorized lists: Accepted, Pending, Sent, and Rejected requests.
  • If a caretaker rejects a request, the patient should not be told it was rejected, and can send a new request freely.
  • If a caretaker accepts a request, both parties are notified and can view each other's profile; the patient profile also displays the accepting caretaker's details, visible to the assigned doctor.
  • Currently, sending a request to a caretaker shows "Caretaker not found." — must be fixed.
  • There is currently no record of a patient's outgoing request visible on the patient's own profile — must be added.
  • Caretakers and patients should each have an option to remove/disconnect from the other.
  • Caretakers should be able to submit a "Request Profile Edit for Patient" on an ongoing basis (not one-time).
  • Add a timeline/history view in both profiles showing this request/connection activity.
4. Profile requirements profiles
4.1 Admin
  • Full access to all doctor, patient, and caretaker profiles and data; full CRUD across all user types.
4.2 Patient
  • Fields: name, DOB, location, languages, phone, nearest emergency contact, gender, marital status, insurance.
  • Medical record updates; past and upcoming appointments; document upload/download support.
  • Filter and choose a caretaker by location, gender, and age, then send a connection request.
  • Remove the current "🩺 Voice AI Health Timeline" section; create a dedicated page for it below "Voice AI Engine."
  • "AI Detected Records" from the Voice AI Health Timeline must also be visible to the assigned caretaker.
  • Add a "📍 View Location" option within the caretaker's view of the Patient Voice AI Health Timeline.
  • Remove the "Patient Profile Preview" section. Patient can delete their own profile.
  • For patients, the first page shown after login should be the AI Voice page.
4.3 Doctor
  • Fields: name, DOB, experience, location, pincode, department, languages, license number, gender, specialization, fee, hours, phone.
  • Calendar view of patient appointments; accept/reject requests from patients or caretakers.
  • Once accepted, read-only access to the named patient's medical records (no CRUD).
  • After a checkup, update the appointment as Missed or Completed. Doctor can delete their own profile.
  • Doctor list shows only appointment-accepted/consulted patients, along with each patient's assigned caretaker.
4.4 Caretaker
  • Fields: name, DOB, experience, location, languages, license number, gender, fee, hours, phone.
  • Views the main list of patients seeking caretakers; can send/receive connection requests.
  • Once accepted, can view the patient's profile and request profile edits when needed.
  • Caretaker profile should only display the list of doctors (not other caretakers). Can delete their own profile.
4.5 Cross-profile visibility
  • Patient profile shows both caretaker and doctor lists.
  • Newly created doctors/caretakers automatically appear in patient profiles; new doctors automatically appear in caretaker profiles.
  • All profile details stay in sync and update across each relevant profile.
5. Video call feature calls
  • All appointment types support video call: doctor–patient, doctor–caretaker consultations.
  • Appointment booking must specify whether it is Online (video call) or Offline (in-person).
  • Only the doctor can initiate a video call for an appointment — not the patient or caretaker.
6. Notifications & Voice AI assistant voice-ai
  • When a patient asks the Voice AI to contact the caretaker, an alert is sent to the caretaker if available.
  • If no caretaker is available, the AI informs the patient and waits for the next command.
7. Authentication & access control auth
  • Sign-up/login supports four user types: Admin, Doctor, Patient, Caretaker.
  • After logout, the browser back button must not restore access to the profile — re-entry requires logging in again.
8. UI/UX & responsiveness ui
  • Rename "Rate" to "Star" everywhere in the UI.
  • Remove "Clinic Location" from doctor profiles. Rename "City" to "Location" (e.g., "Location: Aluva, Kochi"), and auto-populate a "Hospital" name based on the selected location.
  • Overall page layout should be responsive across tablets, Android, iOS, Windows, Mac/PC, and Android TV.
10. AI Voice Engine — emergency detection & alerts emergency
10.1 Detection & logging
  • When a patient asks the Voice AI Engine a question, the AI evaluates whether the query indicates a medical emergency or a condition requiring help.
  • Any question flagged as an emergency or medical-condition concern is logged as a search record on the patient's profile (in addition to normal AI Voice Timeline logging).
10.2 Caretaker alert
  • If the patient has an assigned/connected caretaker, the caretaker receives a real-time popup notification in their profile as soon as the emergency query is logged.
  • Popup format example: "Your patient needs quick assistance — [explanation of condition/query]."
  • The popup includes two action elements: a button showing the patient's current location, and the patient's contact number for immediate follow-up.
  • If no caretaker is currently assigned, no popup is sent (per Section 6, the patient is informed no caretaker is available).

Environment configuration

.env at the project root. Without SMTP configured, emails print to the terminal in dev mode — nothing crashes.

.env
# Django
DJANGO_SECRET_KEY=your-secret-key
DEBUG=True
ALLOWED_HOSTS=*

# JWT
JWT_SECRET=your-jwt-secret

# Database
DATABASE_URL=sqlite:///./beacon_users.db

# Gmail SMTP (requires 2FA + App Password)
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=yourname@gmail.com
SMTP_PASSWORD=your16charapppassword   ← NO spaces
SMTP_FROM_EMAIL=yourname@gmail.com
SMTP_FROM_NAME=Beacon AI Care Unit Platform

# AI / Gemini
GEMINI_API_KEY=your-gemini-key

# Base URL
FRONTEND_BASE_URL=http://localhost:8000
Note: without SMTP config, emails are printed to the terminal in dev mode. No crash.
